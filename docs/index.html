Overview

Support agents could only refund an order in full, so a damaged item meant refunding everything and re-charging the rest. This adds partial refunds: an agent refunds any amount up to the remaining balance, and invalid amounts are rejected before anything is charged back.

Closes #17 · Ticket: SHOP-42

Changes

  • Partial refunds: POST /orders/:id/refunds refunds a given amount and reduces the order balance
  • Validation: rejects zero, negative and over-balance amounts, and amounts above the per-refund limit
  • Storage: a new refunds table records each refund
  • Tests: unit tests for the refund service

Caveats

  • Migration: adds the refunds table; run it before deploying the code.
  • Config: REFUND_MAX_CENTS caps a single refund (default 100000).
  • Limitation: the limit is global, not per merchant (TODO left in refund.py).

QA test scenarios

  • Partial refund: refund 20.00 on a 100.00 order → 201, balance 80.00
  • Full remaining balance: refund exactly the balance → 201, balance 0.00
  • Invalid amount: refund 0 or −5 → 422 "invalid amount", balance unchanged
  • Over limit: refund above REFUND_MAX_CENTS → 422 "over limit"
  • Regression: a full refund through the existing flow still works

Conventional Commits titles

<type>(<scope>)[!]: <description>, following Conventional Commits 1.0.0. The type says what kind of change it is, the scope says which area it affects.

TypeUse forExample
featA new feature or user-visible capabilityfeat(refunds): support partial refunds
fixA bug fixfix(auth): keep the session after a password change
perfA performance improvementperf(search): cache facet counts
refactorRestructuring with no behaviour changerefactor(billing): extract invoice builder

!A breaking change, explained in the Caveatsfix(api)!: reject expired tokens on refresh

FAQ

Does it open the pull request for me?

Only with --create, and only after you confirm the title, base and head. By default it writes the description, copies it to the clipboard and prints the gh pr create or glab mr create command for you to run.

Does it work with GitLab merge requests?

Yes. It reads the host from the origin remote and uses the right words (merge request on GitLab, pull request on GitHub, Bitbucket and Azure DevOps), the platform's size limit and the matching CLI command.

What if my repository has a PR template?

It fills it. .github/pull_request_template.md, .github/PULL_REQUEST_TEMPLATE/*.md and .gitlab/merge_request_templates/*.md are found automatically; their headings and checkboxes are kept, and anything without a home goes under a new heading at the end.

How does it know what's a caveat?

The collector flags candidates from the diff: migrations, dependency and CI changes, env vars read by new code, feature flags, routes, removed public definitions, deleted tests, TODOs, debug output and secret-looking values. Claude checks each against the code and keeps only the real ones, plus any requirement the branch doesn't meet.

Does it change my code?

No. It only writes to the .branch-pr/ folder, which is git-ignored automatically through .git/info/exclude, and nothing is pushed unless you ask.

Big branches?

The diff is written to a patch file with each file's start line, source first and lockfiles left out, so Claude reads it in parts instead of all at once.

Why is the plugin command /branch-pr:branch-pr?

Claude Code namespaces plugin commands as plugin:skill. To type plain /branch-pr, install it as a standalone skill by cloning it into ~/.claude/skills/branch-pr.
